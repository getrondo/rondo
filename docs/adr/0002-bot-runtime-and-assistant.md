# ADR-0002: Bot runtime on Vercel and an AI assistant for admins

- **Status:** Accepted (2026-11-24)
- **Deciders:** maintainers

## Context

The first bot release has to (1) keep the database current from the live group, (2) let admins
run the community from a private chat in plain Ukrainian or Russian, and (3) start running games
itself: sign-up polls with a waitlist, rescheduling, venue moves, cancellations and balanced
line-ups. It must be cheap to run for a ~200-member group with bursty traffic around game times.

## Decision

| Concern | Choice |
|---|---|
| Hosting | Vercel (Fluid compute) running `apps/web`, a Next.js 16 app that only exposes route handlers today and can host the admin web UI later |
| Telegram | Webhook `POST /api/telegram`, authenticated with Telegram's `secret_token` header; updates are handled before the reply, one at a time (`max_connections: 1`), so a failure answers 500 and Telegram retries in order. Commands, menu taps and typed menu input are handled before the reply too; only the model runs in `after()`, because it is slow: the assistant's answer to free text and the proposal of an unknown venue. Outgoing calls go through grammY's `Api` wrapped in the Effect `Telegram` service and give up after 10 seconds. Only a 429 whose `retry_after` ends within 10 seconds of the first attempt is sent again, so a call takes 20 seconds at most; an unknown result is never sent again |
| Forum topics | A community can link several groups: `/link` in another group adds it, the first linked one is the default. One game has one poll: the first group gets it, every further group a forward of the same poll, so votes, the limit, the waiting list and the roster are shared by poll id, and notices, line-ups and waitlist mentions go to every group the poll is in. `/newgame` preselects the groups that weekday was last posted to; the game card opens an open poll to another group with one confirmation. `/link` binds the topic it is sent in (`org.telegram_chat.topic_id`). General, and a group without topics, have no topic id, because Telegram refuses one for General. `message_thread_id` counts only together with `is_topic_message`: replies carry it too. The bot posts to the bound topic, and polls, line-ups, cancellations and places are read only there. Members are learned from every topic |
| Language | The group reads `org.community.default_locale`, `ru` or else `uk`. A private chat follows the user's Telegram language |
| Idempotency | `comms.processed_update` records every `update_id`: a finished one is ignored, a failed one is retried up to three times |
| Database | Neon Postgres 18 (Vercel Marketplace, Frankfurt). Pooled URL at runtime; the unpooled URL runs migrations during production builds only |
| AI | AI SDK 7 through the Vercel AI Gateway (`AiGateway` Effect service, OIDC auth on Vercel). Model `anthropic/claude-haiku-5.5` with gateway fallback to `anthropic/claude-haiku-4.5` |
| Admin menu | `/newgame`, `/games`, `/menu` work by taps without the model. `/newgame` predicts the next game in plain code (football at training places, last 12 weeks, place and time weighted 0.8 per week, the place's usual size, dates from tomorrow) and shows it as the exact poll. A screen and its typed input live in one `comms.admin_state` row per admin (30 minutes): typed text is taken once by revision, ✅ consumes the row once and runs the same pending-action path as the assistant, so the approved preview is checked and nothing runs twice. Every tap rechecks admin rights; stale buttons say so |
| Assistant safety | The model reads through typed tools and writes **only** by creating `comms.pending_action` proposals. The bot renders each proposal from the stored payload (never from model text) with ✅/❌ buttons; only the requesting admin can confirm, their admin access and the community of every referenced game, player and venue are rechecked, proposals expire after 30 minutes, and every executed change is written to `audit.log` |
| Admin access | Owners from `RONDO_OWNER_TG_USER_IDS`; further admins are `org.role_grant` rows (`owner`/`organizer`) granted through a confirmed assistant action |
| Live listener | Group messages reuse the importer's extractors (polls, line-ups, cancellations) and trust only admins, by Telegram user id, never by display name. A cancellation is never applied from text: the admin who wrote it gets a private proposal; message bodies are still never stored |
| Members | Anyone who writes, votes, joins or is shown in a member update becomes a player; leaving and rejoining update the membership. Telegram renames are followed until an admin renames the player. Nobody is linked to imported history by name, because names can be faked: admins merge them |
| Venues | An admin's venue pin creates or completes a venue. An admin poll with an unknown place sends only its title to the assistant model, after the reply, and the admin gets a create-venue proposal. Admins also add, rename, alias and retire venues by chat |
| Sign-ups | The bot posts non-anonymous native polls with two answers (in / out), because Telegram only reports votes on polls the bot sent. Question and answers come from the template in `community.settings.poll`, with a generic default. The poll description carries the place in bold, its address linked to Google Maps and the station, with a route button under the poll; change notices and line-ups show the same place block. One renderer makes the preview in the confirmation and the poll. Too long a poll is refused before it is sent. The poll is pinned when the bot may pin. Goalkeeper stays a sign-up role, and older polls with three answers still count. Capacity overflow goes to the waitlist; a freed seat promotes the earliest waiting player and mentions them in the group |
| Publishing a poll | One transaction creates the game, sends the poll and stores the mapping, the message and the result of the action. The poll and the stopPoll of a delete, which runs under the row lock of the game so votes and a second delete wait, are the only network calls inside a transaction, accepted because each ends after 20 seconds at most. The kickoff is checked again under that lock right before the poll is sent. A refused poll leaves nothing. A second poll is refused while one is open, and so is a poll that differs from its preview. If a write after the send fails, the bot closes the poll and says so. If Telegram does not answer, the action fails as "uncertain, check the group" and is never sent again by itself |
| Publishing a line-up | Every group is sent to outside any transaction. The community lock is held only to check the token of the publish and of the delivery right before the send, which also renews their 60-second claims, and to write the receipt after it. A fresh claim is busy for everyone else, so it protects the send, which takes 20 seconds at most. A message whose receipt cannot be written, or whose claim is gone, counts as uncertain and is sent again only on the admin's tap |
| Team balancing | Snake draft by confidential organizer level (1–10, default 5), keepers spread first, then pairwise swaps that minimise the strength spread |
| Scheduled work | Daily Vercel Cron `GET /api/cron/maintenance` (bearer `CRON_SECRET`): expire proposals, remove the summary and the text of the payload of decided or expired proposals older than 30 days (the decision, its result and the ids stay), finish past games, close the polls of finished and cancelled games, prune update and chat history, refresh analytics. A game becomes played and its attendance is filled in one transaction under the community lock and the row lock of the game: the line-up decides (posted entries, else published teams), manual outcomes win, and sign-ups count, player by player, only without a line-up. A poll that could not be closed is tried again every day |
| Player merges | `identity.merge_person()` moves every single-column foreign key to the surviving person, refuses on conflict (see [ADR-0003](0003-identity.md)), leaves append-only history intact and keeps a tombstone (`merged_into_person_id`) |

## Consequences

- One deployable for webhook, cron and future UI; no long-lived worker to operate.
- Cron on the Hobby plan runs daily; minute-level timers (waitlist offers with deadlines, go/no-go
  checkpoints) need Vercel Queues/Workflow or a Pro plan, tracked in E04/E06.
- The assistant cannot act without a human tap, so a wrong model answer costs a ❌, not data.
- Fixtures and prices are not read live yet; league results still come from imports (follow-up).
